# Организация репозитория

Архитектурный источник: [Program Lifecycle and Evolution — Организация репозитория](architecture/Process%20Plane/Program%20Lifecycle%20and%20Evolution.md#организация-репозитория). Ниже зафиксировано его отображение на Python-проект.

## Области кода

- `src/evertree/application.py` — публичный API `EverTree`, события, запуск и закрытие агента; `src/evertree/_application/` — его внутренние функциональные блоки.
- `src/evertree/core/` — доверенные механизмы исполнения, хранения и обязательной проверки. Их код не изменяется через lifecycle Programs; пакеты организованы по технической ответственности, независимо от графа.
- `src/evertree/processes/` — изменяемые Programs собственных процессов агента. Каталог соответствует **Self/Process** (стабильное имя узла `SelfProcess`), а вложенность — его таксономии `SUBTYPE_OF`. `SelfProcess` принадлежит Self через `PART_WHOLE` и является подтипом общего `Process`; процессы внешнего мира остаются в общей онтологии. Составные шаги процесса описываются через `PART_WHOLE`, а не вложенность подтипов.
- `src/evertree/common/` — переиспользуемые пакеты и модули, не привязанные к конкретному процессу или предметному концепту. Внутри допустима обычная структура Python-пакетов по ответственности.
- `tests/` — проверки поведения, контрактов и интеграции. Это не второй каталог программ.
- `artifacts/` — версионируемые результаты, наборы данных и веса; точная версия адресуется парой `(относительный путь, Git commit)`.
- `.state/` — локальное изменяемое состояние: граф, журнал входов, SQLite DBOS, managed Git-репозиторий Programs и согласованные backup состояния. Репозиторий не копируется в backup: commits сохраняются в Git remote. Рабочие файлы задач и кандидатов одноразовые. Оно исключено из Git.
- `tmp/` и `temp/` — одноразовые рабочие файлы: элементы без изменений более 24 часов автоматически удаляются при запуске приложения и при обслуживании каждые 5 минут; pytest также очищает эти каталоги репозитория перед тестами. Для каталогов проверяется возраст всего содержимого. Ссылки и junction не обходятся; ошибки доступа оставляют файлы до следующей попытки. Системный `%TEMP%` не очищается. Долгоживущие результаты храните в `artifacts/`, а для новых временных каталогов кода используйте `cache.temporary_directory()`: блокировка защищает их до выхода из контекста даже при работе дольше суток. Возраст произвольного файла в `tmp/` не защищает от удаления, если сторонний процесс только читает его.
- `%LOCALAPPDATA%/EverTree/cache/` — общий восстанавливаемый кэш Python, библиотек, Codex и Git для всех агентов и тестов. Исходники EverTree находятся в небольших отдельных окружениях; их изменения не копируют библиотеки. Кэш не входит в backup. Последняя использованная версия каждого компонента сохраняется, старые удаляются после освобождения всеми процессами. Временные профили удаляются при закрытии; остатки аварийных запусков — при следующем обслуживании кэша.

## Локальное приложение

Публичная точка входа — `evertree.application.EverTree`. Его конструктор инициализирует состояние, а `start()` и `close()` управляют временем жизни агента. Внутренние классы с суффиксом `Mixin` в `_application/` группируют методы этого же экземпляра по обязанностям. Они не создаются отдельно, не имеют своих конструкторов и не переопределяют методы друг друга. Это разделение кода одного координатора, а не независимые подсистемы.

| Модуль в `src/evertree/_application/` | Ответственность |
| --- | --- |
| `consciousness.py` | Цикл принятия решений, контекст, назначение бюджетов, проверка ответа и обучение по исходу задачи |
| `execution.py` | Вызовы провайдера, учёт ресурсов, отмена и доставка ответа |
| `programs.py` | Поиск и исполнение Programs, runtime traces, создание и оценка кандидатов, активация |
| `persistence.py` | Состояние, bootstrap, журнал входов, backup/restore и обслуживание |
| `tools.py` | Обработчики инструментов сознания и runtime gateway |
| `prompts.py` | Инструкции модели, схемы структурированных ответов и определения инструментов сознания |

Промпты и контракты версионируются вместе с кодом; файловый загрузчик шаблонов не требуется. Такой подход соответствует [рекомендациям OpenAI по хранению промптов в коде](https://developers.openai.com/api/docs/guides/prompt-engineering#version-prompts-in-code).

Основной путь выполнения: `EverTree.submit()` ставит задачу в очередь; `consciousness._run_queue()` выбирает её и запускает `_execute_task()`; `execution._invoke()` обращается к провайдеру; вызовы инструментов идут через `tools._dispatch_tool()`, а исполнение Programs — через `programs._run_program()`. Решение проверяется в `consciousness`, ответ доставляется в `execution`, состояние сохраняется в `persistence`.

## Граница core и processes

`core` обеспечивает доверенные механизмы и обязательные ограничения. `processes` содержит программы поведения, которые агент может улучшать через проверяемый lifecycle. Процесс составляет план, выбирает действие или предлагает обновление; ядро обеспечивает исполнение, проверяет доступ и применяет допустимые изменения. Обязательное условие принятия программы относится к ядру, даже если агент также имеет Program для проверки своих решений. Переиспользуемые помощники Programs находятся в `common/`, координация приложения — в `application.py` и `_application/`.

Публичные API `core.graph`, `core.memory`, `core.cognition`, `core.learning`, `core.evaluation`, `core.runtime` и `core.sandbox` теперь являются пакетами. Их имена типов, pickle identities и annotation namespaces сохранены. `core.codex` — API Codex; прежний `core.codex_provider` сохраняет namespace существующих типов.

| Пакет ядра | Ответственность |
| --- | --- |
| `graph/` | Хранилище, атомарные изменения и типы графа |
| `memory/` | Traces, provenance, retrieval, retention и типы ссылок |
| `cognition/` | Задачи, бюджеты, внимание и защищённые правила контроля |
| `learning/` | Контракты, estimators, состояние и транзакции обучения |
| `evaluation/` | Результаты, scoring и обязательные критерии принятия |
| `runtime/` | Исполнение, worker IPC и защищённый доступ к Git-коду |
| `sandbox/` | Python-окружения, AppContainer и Job Object |
| `codex/` | Конфигурация SDK, протокол, вызовы провайдера и exec-server |
| `programs/` | Доверенный bootstrap, lifecycle, проверки структуры, tests и эксперименты |

`values.py` остаётся самостоятельным модулем неизменяемых значений без зависимости от хранилища графа. Связанные модули объединяются в пакет, когда такая группа уже существует. Для организации файлов не требуется вводить дополнительное состояние или интерфейс; размеры файлов сами по себе не определяют границы.

## Каталоги процессов и роли

Собственные процессы уже разделены на `TaskManagement`, `CognitiveControl`, `MemoryProcessing` и `Learning`. Имена каталогов получаются из имён процессов в `snake_case`. Корневое служебное имя `SelfProcess` в пути исходников опускается.

```text
processes/                           # Self/Process
  __init__.py
  task_management/                  # TaskManagement
    __init__.py
    planning/                       # Planning
      __init__.py
      _exec.py                      # составляет план / управляет процессом
      _model.py                     # только при наличии модели процесса
  cognitive_control/
  memory_processing/
  learning/
```

Одна Program имеет ровно одну основную роль `exec` или `model`. `_exec.py` выполняет процесс: составляет план, готовит аргументы, выбирает действия и управляет внутренними операциями. `_model.py` описывает, объясняет или прогнозирует процесс. Использование LLM и отсутствие непосредственных effects не определяют роль `model`. Все 24 начальные Programs выполняют внутренние процессы и имеют роль `exec`; пустые `_model.py` не создаются. `meta` допустим только как модификатор `exec` для управления обучаемыми механизмами.

В каждом commit находится одна версия каждой Program; у процесса может быть отдельная Program для каждой роли. Варианты одной программы располагаются в Git-ветках по тому же пути. Каталоги вариантов и уровни `_programs/default` не используются.

Если реализации нужны несколько файлов, её роль становится пакетом, например `_exec/implementation.py` и `_exec/helpers.py`. Каталоги таксономии и служебные role-пакеты различаются однозначно. `__init__.py` каталогов таксономии содержит только docstring, без регистрации или исполнения. Каталоги создаются только для существующих типов и программ. Составной шаг связывается с родителем семантически и не становится автоматически его подтипом.

## Поиск и проверка согласованности

`Program` сохраняет стабильный ID, `git_path`, роль и точку входа; выбор выполняется через `active_exec` / `active_model` и `PROGRAM_FOR_PROCESS`. Имена и пути не заменяют ID. Runtime исполняет код из точного Git commit. Доверенный `core/programs/bootstrap.py` используется при первоначальной установке; после неё маршрутизацию определяет граф.

```powershell
uv run python -m evertree.core.programs.layout
```

Команда строит начальный граф без запуска приложения и проверяет соответствие собственной таксономии исходникам: каталоги, role-файлы, entrypoints, связи и активные слоты. CI запускает её после установки зависимостей, перед остальными проверками. Незарегистрированный код, отсутствующая реализация или рассинхронизация завершают проверку ошибкой.

Для кандидатов тот же валидатор проверяет точный commit относительно рабочего графа до оценки и повторно перед активацией. Неактивное предложение может не иметь файла в `main`; при проверке выбранного кандидата его файл уже обязателен. Код кандидата для этой проверки не импортируется и не исполняется. Прямые импорты другой Program, включая другую роль того же процесса, запрещены; используются runtime-вызовы. Помощники своей Program импортируются внутри её role-пакета.

При изменении имени или родителя согласованно меняются граф, каталог, `git_path` и ссылки/импорты. Неполный перенос блокирует активацию. ID и история обучения сохраняются, прежние пути доступны в соответствующих commits. Поиск по предмету и участникам использует семантические связи, без второго родителя или копии исходников.

## Зависимости и версии

Стандартные/внешние пакеты и помощники собственной программы импортируются обычным способом. Общие утилиты импортируются из `evertree.common`. Другая самостоятельная EverTree Program вызывается через объявленный интерфейс и runtime, без импорта её внутренней реализации.

В `common/` можно вынести алгоритм, оставив в процессе признаки, параметры, веса и специфический код. Совместное использование алгоритма не означает совместного обучения параметров. При изменении общего кода проверяйте все зависящие от него программы; фиксированную процедуру принятия улучшений нельзя изменять косвенно через такую зависимость.

Managed-репозиторий Programs находится в `<home>/.state/program-repository`; активный код — в `main`, конкретная версия определяется commit. Установленное доверенное ядро поставляется отдельно и не попадает в candidate checkout. Каждый candidate — независимый clone в `.state/lifecycle/candidates`, без общих изменяемых Git objects. Активная/default ветка — `main`; альтернативы имеют формат `codex/program/<process-graph-path>/<role>/<candidate-name>`, например `codex/program/Self/Process/TaskManagement/Planning/exec/refine-budget`. Путь процесса берётся из графа, роль различает Programs одного процесса. Название кандидата содержит 1–3 слова, нормализуется в нижний регистр с дефисами; совпадения получают суффикс `-2`, `-3` и т. д. API принимает явный `candidate_name`, иначе использует первые три слова change claim. Недопустимые символы компонентов пути кодируются percent-encoding; `/` сохраняет иерархию. Ветка относится ко всему репозиторию, а `ProgramBranch.program_id` сохраняет стабильный ID программы. При переименовании процесса существующая ветка сохраняет исходное имя; новые ветки получают актуальный путь. Обычный Git merge не заменяет защищённые проверки runtime.

Реализованные модули, ограничения восстановления и команды перечислены в [карте v1](implementation-v1.md).

Удалённая активная ветка Programs — `evertree/programs` в общем remote проекта. Её дерево соответствует локальной `main`; история дополнительно сохраняет commits альтернатив. Локальные неизменяемые tags `<candidate-branch>/<commit>` удерживают точные версии кандидатов, включая версии до amend. Присутствие commit в истории не означает принятия: активность задаётся проверенным выбором. Исполнение и восстановление адресуются точным commit, а опубликованная история не переписывается через force push.
