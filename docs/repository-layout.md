# Организация репозитория

Архитектурный источник: [Program Lifecycle and Evolution — Организация репозитория](architecture/Process%20Plane/Program%20Lifecycle%20and%20Evolution.md#организация-репозитория). Ниже зафиксировано его отображение на Python-проект.

## Области кода

- `src/evertree/core/` — инфраструктура графа и исполнения, включая минимальное доверенное ядро. Сюда не переносят предметные модели ради удобства импорта.
- `src/evertree/processes/` — дерево программ процессов. Этот каталог соответствует корневому концепту **Process**; вложенные каталоги подтипов следуют единственному родителю `SUBTYPE_OF` (отношению «является видом»). Составные шаги процесса не являются его подтипами.
- `src/evertree/common/` — переиспользуемые пакеты и модули, не привязанные к конкретному процессу или предметному концепту. Внутри допустима обычная структура Python-пакетов по ответственности.
- `tests/` — проверки поведения, контрактов и интеграции. Это не второй каталог программ.
- `artifacts/` — версионируемые результаты, наборы данных и веса; точная версия адресуется парой `(относительный путь, Git commit)`.
- `.state/` — локальное изменяемое состояние: граф, журнал входов, SQLite DBOS, managed Git-репозиторий Programs и согласованные backup. Оно исключено из Git. `tmp/` — одноразовые рабочие файлы.

## Каталоги процессов

Каждый процесс имеет одно место. Его программы располагаются рядом в служебном пакете `_programs/`; каталоги подтипов — рядом с этим пакетом. `_programs` не является концептом таксономии. Пример обозначений, а не готовая ветвь:

```text
processes/                          # Process
  __init__.py
  <type_slug>/                      # подтип Process
    __init__.py
    _programs/
      __init__.py
      <program_slug>/               # одна самостоятельная Program
        __init__.py
        implementation.py
        helpers.py                  # внутренние помощники этой Program
    <subtype_slug>/                 # подтип type_slug
      __init__.py
```

Создавайте каталоги по мере появления подтверждённых типов и программ. Не создавайте заранее предметные ветви из примеров документации. Программы самого `Process`, если они понадобятся, размещаются в `processes/_programs/`.

Имена пакетов — допустимые Python-идентификаторы в `snake_case`, без коллизий с зарезервированным `_programs` и другими именами в том же каталоге. Имена и пути не заменяют стабильные ID концептов и программ. Служебные `__init__.py` оставляйте без регистрации программ и побочных эффектов импорта.

Одна Program имеет ровно одну основную роль: `model` или `exec`. `meta` — модификатор только `exec`; `simulation` описывает назначение механизма, а не режим запуска. Не дублируйте программу по папкам ролей. Разные программы/модели одного процесса получают соседние пакеты; пустой служебный `__init__.py` не является отдельной Program.

## Поиск и перемещение

**ProcessConcept** — тип объекта, представляющего процесс в графе; **Program** — стабильная графовая идентичность программы. Текущая программа выбирается через `ProcessConcept.active_model` или `active_exec`; все связанные программы доступны через `PROGRAM_FOR_PROCESS`. `Program.git_path` хранит путь от корня репозитория к её Python-файлу или модулю, например `src/evertree/processes/<type_slug>/_programs/<program_slug>/implementation.py`.

Граф задаёт таксономию и привязки, каталоги отражают их. Runtime получает код по `git_path` из зафиксированного commit. `processes/bootstrap.py` используется однократно при создании агента; последующий поиск использует только граф. Отдельного редактируемого реестра маршрутизации нет.

Поиск по предмету, участникам и другим признакам использует семантические связи. Для него не добавляют второго родителя или копию кода.

Изменение имени или родителя, меняющее путь, должно согласованно обновлять граф, каталоги, `git_path` и затронутые ссылки/импорты. Перед активацией проверяется согласованность. Git и граф не образуют общую транзакцию автоматически: будущая операция переноса должна исключать активацию частично обновлённого состояния. ID и история обучения сохраняются, прежний код и пути доступны по соответствующим Git commits.

## Зависимости и версии

Стандартные/внешние пакеты и помощники собственной программы импортируются обычным способом. Общие утилиты импортируются из `evertree.common`. Другая самостоятельная EverTree Program вызывается через объявленный интерфейс и runtime, без импорта её внутренней реализации.

В `common/` можно вынести алгоритм, оставив в процессе признаки, параметры, веса и специфический код. Совместное использование алгоритма не означает совместного обучения параметров. При изменении общего кода проверяйте все зависящие от него программы; фиксированную процедуру принятия улучшений нельзя изменять косвенно через такую зависимость.

Managed-репозиторий Programs находится в `<home>/.state/program-repository`; активный код — в `main`, конкретная версия определяется commit. Установленное доверенное ядро поставляется отдельно и не попадает в candidate checkout. Каждый candidate — независимый clone в `.state/lifecycle/candidates`, без общих изменяемых Git objects. Ветка относится ко всему репозиторию, а `ProgramBranch.program_id` указывает программу, ради которой она создана. Обычный Git merge не заменяет защищённые проверки runtime.

Реализованные модули, ограничения восстановления и команды перечислены в [карте v1](implementation-v1.md).
